# 采集与转发职责边界讨论

状态：讨论中。2026-10-22 用户要求 grill-with-docs，先确认边界，不修改运行代码。
已实施的[数据设备与转发入口分离](../../docs/adr/0006-separate-forwarding-devices.md)继续作为现状；
Q1–Q13 已明确装配、任务、回调与状态职责；离线计数和降频细则继续讨论，不作为运行代码修改授权。

## 已核实的现状

- [main.c](../../app/main.c) 的 start_points 同时编排 DP、端口、CO、参数存储与恢复、process 初始化和采集启动。
- [acquisition.c](../../app/acquisition/acquisition.c) 完成本地采样、发布与健康检查后调用 tr_forward_service。
  TR 收包本来已有独立工作队列；与本地采样耦合的是首次启动、站号更新及运行恢复检查。
- [CO 初始化](../../modules/collect/src/collect.c) 隐式登记 DP 参数读写后端与参考下发回调。
  CO 后端须先于参数初始化完成首次绑定；未决事务读回要求总线 ready，但不要求周期采集线程先启动。
- [TR forwarding](../../modules/transmit/protocols/modbus/forward.c) 首次 service 负责查表、装配与启动，后续还负责维护。
  配置校验分布在 forwarding、register attach 和 server service，部分入口同时安装状态或路由。
- 参数存储不可用时继续运行、采样/发布/通信维护失败时锁存故障并停止喂狗，均是当前应用策略。
  通用模块报告错误和维护内部恢复状态，并未直接决定产品停机。

## 第一轮：三个独立根决策

Q1，应用装配范围：是否统一编排 DP、CO、TR 和参数加载/恢复的依赖关系，
main 保留硬件、状态管理及显式启动调用？建议是。对外名称与目录随后决定，暂不指定新函数或文件。

Q2，维护与采样关系：是否将 TR 首次启动、站号更新和恢复检查从本地采样周期中分开，
使通信维护与采样分别推进？建议是。暂不决定线程、定时器或工作队列实现，
也不据此改变看门狗复位策略或增加预留栈。

Q3，模块之间的装配方式：是否取消 CO 初始化顺带安装 DP 参数后端的隐式组合，
改为应用装配时显式选择 DP 到 CO 的下发适配？建议是。通用适配仍归模块，应用声明连接关系，
不重复编写通用报文处理或持久化实现。

Q1–Q4 均已确认，见下文；保留本轮问题作为决策背景。

## 已确认：Q1 统一应用装配

用户答复：统一放进 protocol 编排，对外提供一个 init，由 main 调用；
初始化和任务调用分开，modules 提供初始化与任务调用接口，具体协议解析和端口在 protocol 中组合。

已确认的边界：

- app/protocol 统一编排 DP、CO、TR 与参数加载/恢复的依赖顺序，对 main 提供统一初始化入口。
- 初始化与任务调用分离；不继续让周期维护入口兼任首次装配和启动。
- 协议处理能力与实际端口的组合关系由 app/protocol 声明。
- 当前仍是讨论，尚未授权按新边界修改运行代码。

对应[ADR 0007](../../docs/adr/0007-protocol-assembly-lifecycle.md)。

## 已确认：Q2–Q4

2026-10-22，用户答复：

- Q2：由 protocol 在应用层显式创建任务，并编排任务。
- Q3：由模块提供回调函数注册接口，由 protocol 注册，连接 CO 和 DP。
- Q4：应用负责组合；协议解析实现仍由模块提供。

因此后续目标是：

- protocol 拥有 DP/CO/TR 范围内的应用任务创建和编排；模块提供初始化、任务处理能力及所需注册接口。
- 通信任务不依赖本地采样循环逐次驱动；不继续由模块初始化隐式创建自身工作线程或工作队列。
- 初始化、注册、任务调用分别表达，注册顺序由应用装配安排。
- CO/DP 的连接通过模块公开的回调注册接口显式建立；不在 co_init 中隐式安装 DP 后端。
- 可复用协议解析器仍归模块；protocol 选择解析器、角色、点表和实际端口的组合。
- 栈大小与容量沿用 .conf 手动配置约定，不按固件类型预设或预留未来任务。

任务内部逻辑、站号初始化、回调完成语义和状态职责已在 Q5–Q13 确认；
离线计数/降频细则、数据交互和启动约束继续讨论。

## 补充核查：当前任务形态

- CO 有公开 co_poll 单次采集，co_start 另外为每条总线创建内部持续线程。
- TR 初始化会创建独立收包工作队列；重配置还有模块内部共享工作队列，运行维护仍由应用周期调用。
- DP 有同步执行与异步提交接口，另有样本处理、业务处理两个静态线程；dp_process_start 激活初始化计划和定时器，本身不创建这些线程。
- DP 参考业务定时器还有模块自己的 delayable work，当前提交到 Zephyr 系统工作队列；系统队列本身归 Zephyr，
  本轮显式创建的对象范围是 DP/CO/TR 自有执行上下文，不接管 Zephyr 内核和子系统内部任务。
- CO 样本发布当前直接调用 DP；参数反馈通过 DP 样本处理进入参数缓存。DP 到 CO 的下发已用函数指针，
  但由 CO 初始化隐式登记。设备在线状态仍归 CO 自身，不会自动变成 DP 测点。
- 当前本机实际站号点与已保存站号参数是两个点：前者 dp_init 后虽有默认 1，质量仍为 UNINITIALIZED；
  后者由参数初始化加载 NVS。当前没有 saved address 自动覆盖实际站号的路径，来源配置应明确选择。
- DP 样本发布会复制消息，成功只表示提交；处理完成有单独的 ticket 等待接口，队列满按 timeout 返回错误。
- IAP 路由开放前必须完成 iap_start/初始化。它有自己的接收线程和升级日志；参数 NVS 不可用时，
  当前保存参数后重启钩子会阻止升级提交，不能把“普通通信可降级”推断成“IAP 仍一定可完成”。
- 因此“初始化和任务分离”涉及真实的调度所有权，不能只改函数名称。


## 已确认：Q5–Q7

用户答复：

- Q5：应用管理上下文。
- Q6：保留多种方式，由 protocol 初始化设置；可以在 DP 初始化后读取，也可以从 GPIO 初始化。
- Q7：两个方向都显式注册，处理函数可以直接由模块提供。

接受的含义：

- 模块继续负责队列等待、采集期限计算、请求调度和协议状态机；应用不逐点遍历点表。
- protocol 创建、连接和启动执行上下文，模块按工作特点提供线程入口或工作处理能力。
- 站号来源是初始化配置项，不固定为 GPIO，也不强制依赖完整本地采样；DP 初始化后的数据读取、
  GPIO 读取等可以作为不同来源。具体读取哪个 DP 点、是否需要等 NVS 加载，由后续配置契约明确。
- CO 到 DP 的样本交付、DP 到 CO 的下发与读回均显式注册。允许直接注册模块导出的处理函数，
  不强制应用另写只作转调的包装函数；通用适配实现仍归模块。

## 已确认：Q8–Q10

用户答复：

- Q8：初始化直接取得站号并完成本地组装；运行状态按在线/离线的思路设计。
- Q9：站号取得与选择由 protocol 决定，当前写死即可。
- Q10：接受样本交付异步入队、参数下发/读回同步返回实际通信结果，保留原事务完成语义。

修正后的边界：

- 统一 init 完成本地配置、回调连接和模块装配，并在初始化阶段取得站号。
- 不采纳上一轮“站号可在 init 返回后继续等待”的建议，不新增等待站号的运行状态。
- 模块接收 protocol 提供的站号值，取值方式由应用决定。DP/GPIO 等是可选择的初始化来源；
  当前允许静态写死，不增加自动回退、运行期切换来源或动态地址读取框架。用户尚未指定具体常量值。
- 本地初始化结果与通信对象在线/离线分开；远端不在线不等于本地装配尚未完成。
- CO 样本成功交付表示已复制并入队，不表示业务处理完成；下发/读回成功表示通信操作完成，
  受既有超时和事务规则约束，不把北向写完成降格为仅入队。

## 已确认：Q11–Q13

用户答复：

- Q11：分别判断；南向按设备连续若干轮询没有回复判离线。北向离线判断暂不做，后续在 protocol 中处理。
- Q12：南向掉线后可以降低报文轮询频率、调整间隔；北向转发和采集继续正常运行。
- Q13：模块维护状态，protocol 接入，app/status 决定产品显示、健康及看门狗策略。

接受的边界：

- 南向通信状态按 dev_id 独立维护，判据为连续轮询无回复；阈值和“轮询”的计数粒度尚待明确。
- 离线只调整该设备的采集调度，不暂停其他设备、本地采样或北向服务。
- 北向离线检测不纳入本次实现，不新增或主动接入“主站静默即离线”的产品策略；后续由 protocol 编排。
- CO 负责通用设备状态与调度逻辑，提供查询/通知；TR 可提供端口活动/错误基础信息，
  当前不为应用推断北向在线。protocol 显式接入，app/status 决定整机行为。
- 对端离线与本地任务卡死分开。远端设备掉线本身不作为整机停喂狗的原因。
- “转发继续正常”表示服务继续运行；离线测点读取旧缓存还是异常、离线设备的显式下发行为尚未决定。

对应[ADR 0008](../../docs/adr/0008-southbound-offline-polling.md)。

## 补充核查：轮询与转发当前行为

- 当前每台远端有三条 500 ms 周期读，CO 按行分别调度，没有设备级完整采集轮次。
- 同一请求目前可能先记传输成功，后因载荷错误再记失败；累计计数不能直接当作完整轮询次数。
- 设备离线后当前代码仍按原行周期轮询，尚无降频策略。
- 当前采集失败保留 DP 旧值但将对应点质量置为错误，TR 普通值读取返回异常；不会自动正常返回旧值。
- 当前显式参数下发不因设备状态离线而直接拒绝，仍会尝试一次受超时约束的通信/读回。

## 下一轮待定项

Q14，计数粒度：是否把每次实际发出的周期采集请求作为一次计数，而不是等设备全部采集行完成才算一轮？
建议按请求计数，同一请求最多更新一次终态计数；现有每行独立周期继续保留。待确认。

Q15，何为无回复：是否可归属设备的合法应答（含 Modbus 异常应答）表示设备仍在通信，
不作为无回复；本地忙/队列满等未发出请求也不计入；应答超时或没有合法应答才累计？建议是，待确认。
通信状态与测点数据/业务错误分开。

Q16，离线降频方式：是否每个离线设备按可配置的慢周期，仅选择一条已有周期读作探测，
恢复在线后恢复原各行周期，而不是慢周期仍把所有行都发一遍？建议单条探测，待确认。
不自动把 0 周期初始化项或仅下发命令转成轮询。

## 后续设计分支

- Q14–Q16 确认后：阈值、慢周期、探测选择、恢复条件及首次通信状态。
- 转发行为：离线测点缓存/质量响应，显式下发是否仍尝试一次；不自动重放命令。

- 回调细化：样本/命令数据类型、复制、满队列/超时传播及避免循环等待。
- 初始化收尾：任务准备/放行顺序、IAP 前置条件、存储和未决恢复、失败处理、资源与验收。
