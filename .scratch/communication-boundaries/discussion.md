## 已核实的现状

- [main.c](../../app/main.c) 的 start_points 同时编排 DP、端口、CO、参数存储与恢复、process 初始化和采集启动。
- [acquisition.c](../../app/acquisition/acquisition.c) 完成本地采样、发布与健康检查后调用 tr_forward_service。
  TR 收包本来已有独立工作队列；与本地采样耦合的是首次启动、站号更新及运行恢复检查。
- [CO 初始化](../../modules/collect/src/collect.c) 隐式登记 DP 参数读写后端与参考下发回调。
  CO 后端须先于参数初始化完成首次绑定；未决事务读回要求总线 ready，但不要求周期采集线程先启动。
- [TR forwarding](../../modules/transmit/protocols/modbus/forward.c) 首次 service 负责查表、装配与启动，后续还负责维护。
  配置校验分布在 forwarding、register attach 和 server service，部分入口同时安装状态或路由。
- 参数存储不可用时继续运行、采样/发布/通信维护失败时锁存故障并停止喂狗，均是当前应用策略。
  通用模块报告错误和维护内部恢复状态，并未直接决定产品停机。

## 第一轮：三个独立根决策

Q1，应用装配范围：是否统一编排 DP、CO、TR 和参数加载/恢复的依赖关系，
main 保留硬件、状态管理及显式启动调用？建议是。对外名称与目录随后决定，暂不指定新函数或文件。

Q2，维护与采样关系：是否将 TR 首次启动、站号更新和恢复检查从本地采样周期中分开，
使通信维护与采样分别推进？建议是。暂不决定线程、定时器或工作队列实现，
也不据此改变看门狗复位策略或增加预留栈。

Q3，模块之间的装配方式：是否取消 CO 初始化顺带安装 DP 参数后端的隐式组合，
改为应用装配时显式选择 DP 到 CO 的下发适配？建议是。通用适配仍归模块，应用声明连接关系，
不重复编写通用报文处理或持久化实现。

三个问题均待用户回答。

## 后续设计分支

- Q1 确认后：准备/激活阶段、参数恢复顺序、IAP 启动位置及失败降级由谁编排。
- Q2 确认后：初始北向站号来源、运行站号变化、维护触发方式及健康进度如何报告。
- Q3 确认后：DP/CO/TR 的最小公共接口、只启用部分模块时的组合，以及适配实现的归属。
- 三项共同确认后：配置纯校验与激活副作用的界线、启动失败处理、可观察状态与验收场景。
