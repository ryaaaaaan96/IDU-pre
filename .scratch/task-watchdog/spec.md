# status 统一编排的显式登记多任务看门狗

## Problem Statement

当前看门狗通过固定周期翻转 GPIO 驱动外部看门狗，并以主循环的单一进展时间判断是否继续喂狗。
应用还将 DP 的活性检查直接接入整机故障路径。这些隐式约束不能表达各任务不同的处理时间、
正常休眠和有意停用，也不能让使用者按需选择哪些任务应当受监控。

用户希望各任务自行登记允许的最大心跳间隔，由 status 统一调用底层实现监控和喂狗管理。
任一活动登记项超时即触发整机复位；未登记的任务不受到新增监控，也不检查哪些应启动任务尚未登记。
用户还需要用明确标志表达监控永久休眠，在再次启用时重新登记，并在 RAM 中查询当前任务与故障信息。

## Solution

提供显式登记、心跳、监控永久休眠、重新登记及 RAM 查询能力。status 管理监控生命周期和整机故障策略，
在应用层以活动任务链表和一个 Zephyr 内核定时器检测独立期限，底层 GPIO 服务负责周期性喂外部看门狗。
没有活动登记项且无已锁存故障时持续喂狗；活动登记项均按时报告进展时也持续喂狗。

任一活动登记项超时后，先锁存首个故障和任务身份，停止外部喂狗，然后请求软件冷复位。
故障不能被迟到心跳、永久休眠或重新登记解除。普通休眠计入超时预算；
显式监控永久休眠退出超时计时，恢复时重新登记。诊断只放在 RAM，重启后清空。

本轮建立上述能力并解除旧隐式活性约束，不给主采样、DP、CO、TR、IAP 等现有执行上下文增加登记或健康探针。
它们的接入清单保留为后续工作。

## User Stories

1. 作为应用开发者，我希望通过 status 显式登记需要监控的任务，以便自行决定监控覆盖范围。
2. 作为应用开发者，我希望只有登记成功的任务才受到期限约束，以便未接入任务不会被意外判故障。
3. 作为产品维护者，我希望没有活动登记项时持续喂外部看门狗，以便先提供能力而不强制接入现有任务。
4. 作为产品维护者，我希望不检查启动登记遗漏，以便任务创建和功能启用仍由业务编排负责。
5. 作为任务开发者，我希望登记自己的最大心跳间隔，以便不同任务采用适合自身运行周期的时限。
6. 作为任务开发者，我希望登记成功即开始计时，以便获得明确的首次心跳期限。
7. 作为任务开发者，我希望获得明确的登记结果，以便无效配置或初始化错误时不会误以为已受到监控。
8. 作为任务开发者，我希望重复登记活动任务被拒绝，以便不会意外重置原有期限。
9. 作为任务开发者，我希望用独立心跳刷新自己的期限，以便其他任务的活跃不能掩盖本任务失去响应。
10. 作为周期任务开发者，我希望正常休眠包含在超时预算内，以便线程休眠期间不会误触发复位。
11. 作为周期任务开发者，我希望预算覆盖休眠、最长处理时间和调度余量，以便能够适配合理的运行抖动。
12. 作为事件任务开发者，我希望后续能在确认正常空闲后报告进展，以便没有消息不等于失去响应。
13. 作为工作队列维护者，我希望后续由同一队列执行健康探针，以便验证实际处理上下文仍能响应。
14. 作为任务开发者，我希望通过明确业务操作进入监控永久休眠，以便有意停用任务时停止其超时计时。
15. 作为维护者，我希望查询到明确的永久休眠标志，以便区分主动停用和普通等待。
16. 作为任务开发者，我希望停用一个任务不影响其他任务，以便其他活动登记项继续接受独立监控。
17. 作为应用开发者，我希望所有登记项均进入永久休眠时仍持续喂狗，以便监控可以被业务有意停用。
18. 作为任务开发者，我希望恢复监控时重新登记，以便以新的时限开始下一次运行阶段。
19. 作为任务开发者，我希望永久休眠期间的心跳不能自动恢复监控，以便恢复操作保持显式。
20. 作为任务开发者，我希望重新登记失败时继续保持未启用状态，以便不会在保护尚未建立时误恢复业务。
21. 作为任务开发者，我希望 status 不替我挂起或恢复内核线程，以便任务生命周期仍由原业务控制。
22. 作为设备使用者，我希望任一活动登记项超时就触发整机复位，以便局部任务卡住不会长期停留在异常状态。
23. 作为设备使用者，我希望先停止外部喂狗再请求软件复位，以便软件复位未完成时仍保持停喂。
24. 作为维护者，我希望保留首个超时任务，以便后续故障不会覆盖最初的任务身份。
25. 作为设备使用者，我希望故障一旦锁存就不能被迟到心跳解除，以便超时不会被事后的活动掩盖。
26. 作为设备使用者，我希望删除计时或重新登记也不能解除故障，以便活动登记项变成零不会恢复喂狗。
27. 作为维护者，我希望查询任务名、时限、最后心跳和当前监控状态，以便理解当前登记情况。
28. 作为维护者，我希望查询首个故障的 RAM 快照，以便调试当前运行期间的任务超时。
29. 作为维护者，我希望查询得到一致快照，以便并发心跳或休眠切换不会产生混合状态。
30. 作为产品维护者，我希望诊断不跨重启保存，以便不增加参数区格式、Flash 写入和故障现场保存流程。
31. 作为设备使用者，我希望超时处理不等待其他任务或工作队列，以便阻塞任务不会阻止复位动作。
32. 作为模块维护者，我希望复用 Zephyr 内核定时器及既有 GPIO 能力，以便不为每个任务创建监控线程。
33. 作为模块维护者，我希望通用模块继续独立于应用 status 头文件，以便以后通过显式回调接入。
34. 作为配置维护者，我希望通过常驻上下文提供登记存储并配置 GPIO 喂狗周期，以便控制 RAM 和硬件时序。
35. 作为配置维护者，我希望任务时限由登记调用传入，以便不生成按固件类型预设的任务表。
36. 作为应用开发者，我希望旧主循环和 DP 隐式活性限制被解除，以便没有登记时确实持续喂狗。
37. 作为设备使用者，我希望明确的初始化失败和 GPIO 故障仍受现有整机故障策略处理，以便不会被零登记规则清除。
38. 作为设备使用者，我希望远端设备离线继续保持业务降级，以便通信故障不会直接变成任务超时。
39. 作为升级维护者，我希望保持 MCUboot 与应用对外部看门狗的板级交接，以便不改变原有启动和升级约束。
40. 作为维护者，我希望本轮不自动接入现有任务，以便以后逐项确定时限、检查点及正常空闲行为。
41. 作为维护者，我希望区分模拟器验收和实板复位验证，以便不会把 GPIO 模拟结果误认为硬件已经验证。

## Implementation Decisions

1. **职责归属。** status 是应用侧统一入口，负责登记关系、RAM 诊断、故障锁存和重启策略；应用层一个 Zephyr 内核定时器跟踪最早到期期限，现有 GPIO 看门狗模块负责外部喂狗边沿及停止动作。保持当前命名风格和模块依赖方向。
2. **初始化。** 随现有 status 初始化准备任务监控能力及 GPIO 喂狗服务，不要求再为各任务创建监控线程。活动链表只由显式登记建立，启动时不扫描线程或自动补齐登记。
3. **登记对象与配置。** 调用者持有常驻任务上下文和名称，配置包含非零 uint32_t 毫秒时限。复制必要配置值，活动链表和期限由 status 管理；上下文和名称必须覆盖监控及诊断查询的生命周期。永久休眠使用明确标志，不把特殊时限值当作永久休眠。
4. **公开接口。** 提供 status_register、status_feed、status_sleep_forever，以及任务快照和首个故障快照的查询接口。登记成功返回成功结果并立即开始计时；正常活动任务重复登记返回错误，不修改已有期限。
5. **错误契约。** 未初始化时拒绝登记；无效上下文、名称或零时限返回参数错误；不使用固定通道数组或堆分配，不设置容量配置；未登记或永久休眠的任务不能通过心跳建立或恢复监控。所有调用方能够区分操作成功与失败，不静默忽略错误。
6. **独立期限。** 心跳只刷新对应活动登记项。登记时限覆盖正常休眠、最长处理及调度余量；不根据收到报文数量自动判健康，不自动延长期限或在错误后自动停用监控。
7. **永久休眠。** 显式操作取消该任务底层计时，保留 RAM 状态和永久休眠标志，不影响其他活动登记项。重复进入永久休眠可以保持幂等；本接口不执行线程挂起、唤醒、删除或恢复。
8. **重新登记。** 永久休眠的同一逻辑任务可重新登记，成功后清除休眠标志、使用本次配置并建立新期限。失败后保持休眠。已休眠任务和迟到定时事件不能改变另一个任务或新的登记周期。
9. **喂狗判定。** 无已锁存故障时，零活动登记项或全部活动登记项在期限内，都允许 GPIO 服务持续喂外部看门狗；全部永久休眠与零活动登记项具有相同的允许喂狗结果。活动登记项数量不是系统故障的判断依据。
10. **超时顺序。** 任一活动登记项超时，先锁存首个故障及任务身份，再停止外部喂狗，然后请求软件冷复位。停止动作不等待主采样循环、其他任务、工作队列或日志处理。后续超时不覆盖首个故障。
11. **故障不可撤销。** 超时锁存后，迟到心跳、永久休眠、重新登记和零活动登记项均不能恢复喂狗或清除故障。运行期不提供解除已锁存超时的接口；查询本身不改变状态。
12. **并发与上下文。** 登记、心跳、休眠及查询面向正常线程调用。共享状态需同步，诊断读取返回一致快照；超时回调按计时器中断上下文处理，只执行中断安全的锁存、停喂和复位，不直接调用包含 LED 操作的完整故障处理函数。
13. **外部看门狗的角色。** 当前 GPIO 封装不是 Zephyr watchdog device，本轮不将其伪装为 Task Watchdog 原生硬件 fallback，也不擅自绑定未知型号的专用芯片驱动。外狗保障是超时回调先停喂，软件复位未完成时也保持停喂；不宣称等价于原生硬件 fallback 的全部能力。
14. **旧隐式约束迁移。** 移除或解耦旧主循环 1500 ms 进展期限及应用默认 DP 活性超时，不把这些未登记执行上下文继续挂在任务看门狗上，也不通过自动登记绕过本轮排除项。通用 DP 活性查询能力可以保留，但不能继续默认触发未登记任务的时限故障。
15. **既有业务策略。** 明确初始化失败、GPIO 错误等现有整机故障仍可锁存并停喂；南向设备离线、参数存储降级继续遵循既有业务边界。startup、STATUS_RUN、采样/转发编排及升级保存保护的既有行为保持，只有本规格明确替代的隐式活性约束改变。
16. **RAM 诊断。** 记录任务名称、登记时限、最后心跳、活动/永久休眠状态以及首个超时任务的快照。名称可由调用者常驻保存，不强制复制字符串。不新增跨重启记录、Flash/NVS 写入、保留内存或备份寄存器机制。
17. **配置与资源。** 任务登记逻辑固定编入应用，不配置 CONFIG_TASK_WDT*；活动项使用调用者上下文串联，无固定容量或堆分配。一个内核定时器跟踪最早期限，每次重排遍历活动项；零活动项时停止检查定时器。GPIO 周期继续取自产品配置。任务时限通过登记接口显式提供；不按固件类型预设任务清单，不给未来任务创建线程栈。任务登记不引入按任务分配的监控线程或输出日志工作队列。
18. **现有任务暂不接入。** 本轮不修改主采样、DP、CO、TR、IAP 的执行循环来增加登记、心跳、健康探针或进展回调，不自动监控 Zephyr 内部线程。后续接入时才按有界等待或同队列探针证明正常空闲。
19. **启动与镜像边界。** 保持 MCUboot 将喂狗 GPIO 浮空禁用、应用重新启用的交接。不新增必需任务就绪清单、启动登记窗口或未登记任务的镜像确认条件，既有明确业务确认条件继续有效。
20. **先例与决策。** 本规格落实 ADR 0009。ADR 0007 的任务归属、ADR 0008 的远端离线不停止整机喂狗继续有效；旧隐式主循环/DP 活性约束由本规格明确替代。

## Testing Decisions

1. **主接缝。** 建议以 status 公开登记、心跳、永久休眠和查询接口为唯一主要功能测试接缝，驱动真实应用层检测、Zephyr 内核定时和 GPIO 看门狗实现。测试边界已向用户征询，本规格先采用这一推荐方案。
2. **外部边界替身。** 只在 GPIO 硬件输出与整机复位边界提供设备替身或模拟器，观察实际边沿、停喂、复位请求及 RAM 公开快照。不得用固定成功的内部通道替身代替超时算法，不直接读取或修改私有链表、定时器对象或锁。
3. **既有先例。** 复用 io 套件通过 GPIO API 和模拟设备检查输出及错误传播的方式，acquisition 套件检查真实启动/status 流程的方式，以及 IAP 套件在系统复位边界替换函数的方式。只按改变的职责调整旧断言。
4. **复位语义。** 本功能超时发生在计时器中断上下文，不能照搬现有 IAP 在线程中永久休眠的复位替身。复位边界测试必须保持不返回契约，采用独立 native 进程、原生退出机制或等价外部边界捕获；不得在 ISR 睡眠，或让标注不返回的系统函数直接返回。
5. **基础矩阵。** 覆盖零登记持续喂狗、多任务不同期限、只刷新一个任务不能保护另一个任务、正常预算内休眠、无效配置、未登记操作、活动任务重复登记及超过原固定容量的批量登记。
6. **生命周期矩阵。** 覆盖单任务/全部任务永久休眠、明确标志及 RAM 快照、同一逻辑任务恢复、重新登记失败保持休眠、永久休眠期间心跳不自动恢复，以及活动项移除与重新登记不会串扰。
7. **故障矩阵。** 从真实超时进入故障，验证先锁存、再停喂、再请求复位；软件复位边界已到达时 GPIO 喂狗已停止。首个故障不被后续操作覆盖，迟到心跳或重新登记不能恢复。普通 GPIO 错误和明确业务故障的既有终止行为继续验证。
8. **集成回归。** 更新现有 acquisition 与 io 的旧隐式超时断言，验证零新登记时不再因原主循环/DP 期限停喂，现有任务没有被自动登记；采样、业务故障、LED、镜像确认和协议启动顺序等相关行为继续回归。
9. **时间与隔离。** 使用原生模拟器可控运行时间和有余量的期限，避免卡在单个调度 tick 边界。全局故障不可清除，故障场景通过新进程隔离，不能为了复用用例添加产品清故障接口。
10. **构建与实物。** 完成必要模块/native 回归及当前 MCUboot + IAPv3 固件构建、签名和产物检查。实板另行检查 GPIO 边沿、停止喂狗后的复位、软件冷复位及 MCUboot 交接，不能以模拟器通过代替硬件证据。

## Out of Scope

- 本轮给主采样、DP 样本/业务处理、CO 总线、TR 接收/配置队列或 IAP 工作线程增加实际登记、心跳或探针。
- 自动扫描线程、维护必需任务清单、检查从未登记的应启动任务、设置登记启动窗口。
- 自动识别业务空闲、自动代喂、错误后自动停用、自动延长长操作期限。
- 自动挂起、恢复、终止内核线程或回收其栈；监控永久休眠只改变监控关系。
- 任务故障后自动恢复继续运行，或提供运行期清除已锁存超时的能力。
- 跨重启诊断保存、故障现场 Flash 写入、NVS 格式变更、保留内存和备份寄存器接入。
- 新增未知外狗型号的设备驱动、改变物理引脚或 GPIO 时序、改动上游 Zephyr/MCUboot 仓库。
- 新增远端设备在线判定、北向离线检测、协议报文或参数事务策略。
- 把本轮验收当作所有现有任务已经受到监控或真实硬件已经完成验证。

## Further Notes

- 本规格发布到项目本地 Markdown 任务跟踪目录，实施后标签改为 implemented；不创建远端 Issue，不推送。
- 用户最后明确选择 RAM 诊断、不提供跨重启保存，替代讨论中对“RAM 暂时不保存”的短暂误读。
- 本规格已按三个任务实施并完成桌面验收，见[验收记录](validation.md)及[两轴审查](review.md)。取消旧隐式活性约束是落实零登记规则的必要修改，不代表本轮替现有任务增加监控。
- 后续任务接入时，再逐项确定期限、正常空闲检查点、工作队列探针及升级/存储长操作预算。

## 实施后的用户修正

用户明确要求将 CONFIG_TASK_WDT 对应逻辑移至应用层，不增加任务看门狗配置。
本规格已同步为单个内核定时器与调用者上下文链表；此前固定通道容量及复用 Task Watchdog 子系统的决定已被替代。
原三任务验收保留为历史记录，当前验证见[应用层实现记录](application-timer.md)。
