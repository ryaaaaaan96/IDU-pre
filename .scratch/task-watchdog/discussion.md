# 多任务看门狗边界讨论

状态：设计已确认并实施，见[验收记录](validation.md)。本文件保留设计时的事实与问答；当前行为见 [多任务看门狗方案](../../docs/task-watchdog.md)。

## 用户目标

- 监控多个任务，每个任务自行注册自己的喂狗时限。
- 任一受监控任务超时后整机重启。
- 希望由应用 status 组织这部分功能。

## 设计时核查的事实

- 当前 modules/watchdog 通过 GPIO 每 10 ms 给外部看门狗提供边沿，以主循环最后进展时间和 1500 ms 窗口决定是否继续喂狗。
- Zephyr task_wdt 支持多个独立通道的 add/feed/delete；注册即计时，默认超时处理为冷复位，自定义回调位于内核计时器中断上下文。
- 当前 GPIO 外狗封装不是 Zephyr watchdog device，不能直接作为 task_wdt_init 的硬件 fallback 参数。器件型号尚未确定，不能直接套用特定器件驱动。
- DP samples、CO bus、TR receive 等上下文正常情况下也可能永久等待工作；无消息不能直接判定为故障。模块需要通用进展接入方式，不能依赖应用 status 头文件。
- ADR 0008 明确远端离线不停止整机喂狗；任务健康与远端通信状态需要区分。

公开能力说明：[Zephyr Task Watchdog](https://docs.zephyrproject.org/latest/services/task_wdt/index.html)。

## 已确认

- Q1：有限休眠计入任务的超时预算，预算覆盖正常休眠、最长处理时间及调度余量。
- Q1 补充：通过明确标志位表达监控永久休眠；该任务暂时退出监控，再次启用时重新登记。
- Q2：由 app/status 编排并调用底层能力实现功能。
- Q3：超时后锁存任务身份、停止外部喂狗，再尝试软件复位；故障路径不等待其他任务、不写 Flash。
- Q4：无限等待事件的任务也定期证明响应能力。普通线程使用有界等待后的检查点；工作队列由同一受监控队列执行健康探针。
- Q5：永久休眠仅由明确业务操作进入；恢复时先重新登记，成功后继续业务。已超时锁存的故障继续重启流程。
- Q6：不维护必需任务清单、不检查启动登记遗漏；只有用户显式调用 status 登记接口的任务才纳入新增监控。
- Q7：本轮不接入现有任务，只确定按需登记能力；主循环、DP、CO、TR、IAP 的实际接入留待后续。
- Q8：没有活动登记项时持续喂外部看门狗，由 status 统一管理；不保留未登记任务的隐式 1500 ms 活性约束。已锁存故障继续停喂和复位。
- Q9：以用户最后的“RAM，不提供跨重启保存”为准，诊断保存在 RAM，重启后清空，不增加持久化记录。

## 生命周期含义

监控永久休眠是显式退出运行时限监控的状态，与正常 k_sleep、等待报文、系统低功耗区分。
活动登记项在普通休眠及事件空闲期间继续受监控；标记永久休眠后不要求心跳，恢复时建立新的登记周期。
此状态并不自动执行内核线程挂起或恢复，实际任务启停的编排边界仍需落实。

## 后续接入清单（本轮不实施）

- 主采样循环。
- DP 样本处理和业务处理。
- CO 每条采集总线。
- TR 接收队列和配置维护队列。
- 启用 IAP 时的升级工作线程。

未来按任务实际行为增加检查点或同队列健康探针；不修改 Zephyr 内部线程。

## 收敛结果

本轮问题均已明确，形成 [ADR 0009](../../docs/adr/0009-opt-in-task-watchdog.md)。
方案实施时需解耦当前主循环租约和应用中默认 DP 活性检查，避免未登记任务仍触发看门狗超时；
不为这些任务自动增加登记来替代旧路径。实施已完成，旧隐式约束已解除，现有任务仍未登记。

不引入启动登记窗口、必需任务列表或超时历史持久化；长操作的允许时间由调用者登记的预算覆盖。
