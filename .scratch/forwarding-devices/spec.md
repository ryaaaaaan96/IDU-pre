# 数据设备与虚拟转发设备分离

## Problem Statement

当前 IDU 将本地数据、南向采集目标、北向转发表与 IAPv3 协议段装进同一种设备挂表结构。
维护者必须理解固定七个协议槽、首槽必须是 process 的限制，以及额外的转发服务关联。
本地设备被同时用作北向入口的配置容器，容易混淆数据归属、北向站号与南向站号。

普通转发表目前合并成全局映射，选择挂表设备并不能隔离不同北向入口的地址空间。
仅增加一个虚拟设备条目既不能消除首槽限制，也不能让多个入口安全复用相同寄存器地址。
用户希望借鉴参考项目独立虚拟转发设备的设计，同时减少应用配置和无效占位。

## Solution

应用维护两类声明：数据设备声明本地或远端数据及其可选采集关系；虚拟转发设备声明
北向逻辑口、所用转发表、协议段及广播策略。模块解释配置并完成校验和装配，应用不再
为一个北向入口重复维护本地设备挂表、独立寄存器服务对象及协议指针。

虚拟转发设备引用已有数据设备的测点，不创建 process 表或复制数据缓存。
每个入口独立选择转发表和协议段，普通读写均在该入口的地址空间中解析。
北向站号继续由拨码在运行时传入；两台南向设备继续在同一采集逻辑口轮询。
现有 process 回调、参数持久化、IAPv3 和应用收发编排继续保留。

## User Stories

1. 作为配置维护者，我希望分别声明数据设备与虚拟转发设备，以便直接理解数据来源与协议入口的区别。
2. 作为配置维护者，我希望本地设备只关联自身 process 表，以便本地采样不再承担北向转发身份。
3. 作为配置维护者，我希望南向设备关联 process 和 collect 表，以便集中查看其测点、采集口和站号。
4. 作为配置维护者，我希望没有 collect 表的设备不生成采集目标，以便本地设备不需要虚假的通信配置。
5. 作为配置维护者，我希望两台同型远端设备共用 const 点表，以便仅改变设备 ID 和站号即可添加实例。
6. 作为配置维护者，我希望每行配置显式填写有效字段，以便避免隐藏在整行宏中的协议关系。
7. 作为配置维护者，我希望可选项使用所属模块提供的缺省字段值，以便不用手工填满七个协议槽。
8. 作为配置维护者，我希望点表继续分文件登记并自动计数，以便不维护 extern 数组数量或包含其他 C 文件。
9. 作为配置维护者，我希望北向入口直接选择转发表和协议段，以便不依赖本地设备在数组中的位置。
10. 作为配置维护者，我希望转发身份与数据设备 ID 分开解释，以便相同数值不会误指向一个数据来源。
11. 作为协议维护者，我希望一个转发表能引用本地和多台远端设备的数据，以便组合统一的北向协议。
12. 作为协议维护者，我希望两个转发入口能使用相同寄存器地址映射不同测点，以便独立维护各入口协议。
13. 作为协议维护者，我希望不同入口也能共用同一张转发表，以便复用协议而不复制表内容。
14. 作为协议维护者，我希望读、写、协议段分派与冲突校验都使用当前转发入口，以便避免只隔离读取而写错设备。
15. 作为协议维护者，我希望非法表引用、错误表类型和冲突绑定在启动时明确报错，以便及时发现配置问题。
16. 作为北向主站，我希望普通读取仍返回 DP 中已采集的值，以便保持缓存读取行为而不触发额外南向请求。
17. 作为北向主站，我希望写入按当前入口映射到正确的设备和信号，以便同地址的另一个入口不受影响。
18. 作为业务开发者，我希望设置、读取、状态和命令回调继续由 process 表定义，以便业务逻辑不会迁回通信配置。
19. 作为业务开发者，我希望转发设备只引用现有测点，以便不会产生第二份状态、参数或缓存。
20. 作为采集维护者，我希望采集调度与北向请求分别执行，以便配置拆分不破坏已有线程职责。
21. 作为采集维护者，我希望毫秒周期继续使用 uint16_t 并支持 60000 ms，以便维持刚确认的周期配置方式。
22. 作为采集维护者，我希望零周期保留初始化读取与仅下发的区别，以便不会误把命令变成轮询项。
23. 作为配置维护者，我希望北向站号仍来自拨码采样并在运行时更新，以便不在静态配置中重复维护站号。
24. 作为配置维护者，我希望南向站号独立于北向站号，以便现有不同站号的同线测试继续工作。
25. 作为端口接入维护者，我希望应用继续注册完整报文收发回调，以便物理端口编排仍由应用负责。
26. 作为端口接入维护者，我希望 vport 保持协议无关，以便配置调整不引入硬件或 Modbus 专属后端。
27. 作为设备使用者，我希望持久设置继续写入参数区并在重启后恢复，以便配置结构调整不会丢失已保存值。
28. 作为设备使用者，我希望非持久命令仍只执行一次，以便重启或恢复流程不会重放命令。
29. 作为设备使用者，我希望未决南向设置继续通过读回确认，以便丢失应答时不盲目重发。
30. 作为升级工具使用者，我希望原 IAPv3 地址段、变长报文及广播行为保持，以便升级工具无需更改。
31. 作为升级维护者，我希望升级段只在被配置的入口生效，以便另一个入口不会借用全局升级映射。
32. 作为模块维护者，我希望通用装配和协议解析留在模块中，以便应用只维护产品配置与业务回调。
33. 作为模块维护者，我希望未使用模块及适配器的现有可选构建仍通过，以便采集与转发可以独立复用。
34. 作为测试维护者，我希望通过已有完整报文入口和假南向回调验证功能，以便测试不依赖私有结构布局。
35. 作为产品维护者，我希望记录 Flash、静态 RAM 和实板验证范围，以便区分结构简化与实际资源收益。

## Implementation Decisions

1. 使用已讨论的两类配置。`data_device_cfg` 表达数据设备，字段包括 `dev_id`、
   `process_table`、`collect_table`、`collect_port`、`collect_addr`；`tr_forward_cfg` 表达
   虚拟转发设备，字段包括 `forward_id`、`port_id`、`transmit_table`、`protocol_segments`、`route_broadcast`。
   数据设备和南向站号沿用现有 8 位配置范围；表标识与转发身份为 16 位，广播策略为布尔值。
2. 数据设备必须关联非空 process 表。collect 表标识为零时不生成南向目标，也不解释其端口和站号；
   非零时必须找到正确类型的表并校验有效采集逻辑口、Modbus 站号及测点关联。
   本地 IDU 与远端设备 10、11 保持原数据身份；后两者共享模型表、使用采集逻辑口 0 和站号 1、2。
3. 虚拟转发设备无需 process 表、不进入 DP 测点池、不成为参数存储键。
   `forward_id` 与数据 `dev_id` 属于不同身份空间；各空间分别检查重复标识，数值相同不代表同一对象。
   转发行继续通过原有 `dev_id` 和 `sig_id` 选择数据。
4. 每个转发入口必须选择非空转发表，可选择协议段表；协议段标识为零表示没有协议段。
   转发表与协议段直接归属转发配置，不通过数据设备挂载，也不以数组第一个元素隐式选取。
   模块装配现有服务生命周期、请求路由与写入处理，产品不重复维护 `idu_registers` 和额外协议关联。
5. TR 普通读写必须使用当前入口选择的表，移除产品路径中把所有转发表合成全局命名空间的依赖。
   允许不同入口将同功能码、同寄存器地址映射到不同测点，也允许入口共享 const 表。
   同一入口内保留已支持的完整点读取及重叠兼容规则，不新增覆盖优先级；原本非法的重复映射仍拒绝。
6. 地址解析由 TR 完成，再把设备/信号键交给 DP。DP 继续负责 process 回调、值校验、事务及参数持久化，
   CO 负责按数据设备定位南向目标并执行采集或下发。旧地址式接口如继续提供，必须有明确入口上下文，
   或在无法唯一确定入口时拒绝；不能默默选择另一入口或恢复全局映射来掩盖歧义。
7. 新配置装配契约与校验归通用模块，TR 提供转发配置解释和入口映射选择；执行模块各自取得所属视图。
   应用只提供配置声明、业务回调、启动调用和物理收发编排。DP 不为某个产品创建专用转发设备，
   CO 不解析北向地址，vport 不解释 Modbus、不选择点表，也不接管 GPIO、CAN ID 或串口硬件。
8. 保留 Zephyr Iterable Sections 的点表登记和自动计数，表及配置为静态 const，启动后不替换。
   两类配置不要求应用维护七个通用协议槽、整套指针视图或平行数量枚举。
   静态声明逐字段初始化，可选默认值由解释该字段的模块提供，不新增整行配置宏。
   同型设备的 LISTIFY 批量声明方式继续可用。
9. 北向 unit 继续由拨码采样得到，在现有运行期生命周期调用中更新，不加入静态转发配置重复保存。
   南向站号由数据设备配置明确提供。首轮沿用每个北向逻辑口一个活动入口的模型，
   冲突绑定应报错；独立地址空间通过不同逻辑入口验证，不新增同一接收接口的多站号分派。
10. Modbus 采集行继续直接使用 `uint16_t period_ms`，零周期语义及产品 500 ms 配置不变，
    支持 60000 ms 和 65535 ms 的配置读取，不恢复周期编码转换。
    北向读取仍使用缓存，需要下发的操作仍按 process 的 FLAG_COLLECT 语义交给 CO。
11. 状态与命令保持 process 设置/读取回调行为，命令触发值不缓存、不持久化、不在初始化时重放。
    持久参数的逻辑键、类型、默认值、范围及 NVS 版本不因转发入口分离而改变。
    保留单参数记录、批量提交日志、未决南向意图和读回恢复，不能因配置迁移触发参数区清空。
12. IAPv3 继续使用原三字段协议段，按请求首地址在标准寄存器 PDU 校验前分派；
    回调继续负责精确长度、功能码、变长载荷及会话所有权。命中后的错误不回退普通点表或写入路径。
    广播策略按入口解释，普通点表广播仍静默且不执行业务写，保留现有升级入口和显式广播行为。
    IAPv3 关闭时不登记其入口，且不会改变 IDU 的业务点表方案。
13. 同一 RS485 上的采集/转发收发编排、完整南向事务锁及应答归属检查保留。
    配置和线程职责分开不等于物理链路可同时发送，也不增加外部多主仲裁保证。
    RAW ADU、RTU 组帧、CRC、DE 与发送完成/错误处理继续沿用各自已有职责。
14. 尽量保持现用 dp_/co_/tr_ 点表内容和接口语义；为实现入口隔离而必须改变的绑定、路由和读写接口应同步迁移调用者。
    不维护两份产品配置或通过隐式默认设备兼容旧关联；原生及参考表消费者的可选能力应明确验证。
    当前产品仍只使用一条采集总线、一个转发入口，不新增预留线程栈或固件类型预设，测试容量显式配置。
15. 配置校验覆盖缺表、表类型错误、重复身份、无效端口、缺失数据来源及非法映射。
    校验失败应返回明确错误，不启动失败入口，不用新配置替换仍有效的入口或产生南向写入副作用。
    不要求模块提供热替换或任意初始化副作用回滚。

## Testing Decisions

1. 首选一个集成测试场景作为主要测试接口：登记两类配置，经现有 CO/TR 完整报文输入进入模块，
   用现有南向收发回调提供设备回复，通过北向完整响应、DP 公共查询和发送计数观察结果。
   不为本功能增加测试专用路由器或导出私有结构；白盒断言不能代替外部行为验收。
2. 核心场景配置本地数据与两台远端设备，并建立两个测试用北向逻辑入口。
   两个入口用相同功能码和地址指向不同的已有测点，分别验证读响应和写入目标，
   再验证同一张表被两个入口共用时仍引用同一份数据。测试自行配置所需容量，不扩大产品预留资源。
3. 地址隔离必须通过真实请求选择验证：不能仅检查两个配置对象的字段或编译后的计数。
   在另一入口更新其目标后，应证明原入口未被改写；缺失映射返回既有错误，不从其他入口借表。
   同入口非法重复映射、跨空洞请求、半个多字参数和整批校验失败继续拒绝且没有部分写入。
4. 沿用 `reference_config` 与 `table_registry` 的注册/装配先例验证缺表、错误类型和身份冲突，
   不依赖数组排序、七槽布局或内部 reader 的具体实现。失败不应启动失败入口或产生南向写入。
5. 沿用 `points`、`forwarding`、`shared_rs485` 的公开行为验证缓存读取、周期采集、来源设备身份、
   同线北向与南向不同站号、一次性命令、process 读取回调及状态快照。
   60000 ms 与 65535 ms 只需验证配置正确传入和既有调度类型，不用等待真实 60 秒制造慢测试。
6. 沿用参数重启探针与 `parameter_records` 的独立进程 Flash 文件方法，
   证明原数据设备的已保存值在绑定方式改变后仍能加载，不触发 STORAGE_RESET。
   继续保留批量掉电、丢失应答、未决意图只读回不重放等行为回归。
7. 沿用 `iap` 与扩展 `communication` 报文夹具，验证只有绑定 IAP 段的入口可以处理升级地址，
   并保持完整大载荷、广播白名单、段命中错误不回退、会话互斥和失败短路。
   同一全局 IAP 接收器的现有会话规则不改为每入口独立会话。
8. 继续运行 DP/CO/TR 独立模块及关闭适配器等可选构建，最后运行完整主机/native 回归与
   当前 IDU／MCUboot／IAPv3 构建、镜像验签及导出检查。记录 Flash/RAM 变化，不承诺未经测量的节省。
   仿真通过不代替实际 RS485 时序、运行时栈余量和 NOR 掉电验证。

## Out of Scope

- 实现 CAN、以太网或新的 Modbus 传输协议、分帧、CAN ID 筛选。
- 同一物理接收接口同时响应多个北向 Modbus 站号，或新增外部多主 RS485 仲裁。
- 运行期动态增删设备、替换点表、热切换国家参数或扩展升级并发会话模型。
- 新建虚拟转发 process 点表、独立测点数据池、复制已有参数或重编号现用数据设备与信号。
- 改变采样工程单位、产品寄存器布局、持久化格式、Flash 分区、密钥、升级线协议或签名策略。
- 恢复旧 MV-IO、AIDC 产品分支、ARC 包装层、旧整体快照迁移或逐行表生成宏。
- 完全复刻参考库未公开的多端口映射选择行为，或新增无实际需求的协议槽及线程栈。
- 本次规格发布直接实施运行代码；实施由关联任务承接。

## Further Notes

- 2026-10-22，用户在查看两种结构和 IDU 配置示例后表示“我觉得这样可行”，并调用 to-spec。
  本规格直接综合已讨论方案，不再增加访谈或要求重新批准测试接口。
- 参考项目已确认存在没有 process 表的虚拟转发设备，但未证明闭源库的多入口映射隔离机制。
  本规格的入口隔离是 IDU 明确的新契约，不宣称与参考库二进制或所有隐含行为相同。
- [ADR 0006](../../docs/adr/0006-separate-forwarding-devices.md) 接受数据归属与北向入口分离，
  替代 ADR 0003 中把协议段挂在数据设备上的装配选择，保留原有协议处理行为。
- [结构示例及源码核查](../../docs/forwarding-model.md) 提供背景；本规格是实施验收依据。
- [关联实施任务](issues/01-separate-data-and-forwarding.md) 已标记 ready-for-agent。
- 发布时只验证文档一致性、链接与 Git 差异，未运行或宣称完成实现测试；现有用户未提交改动保持不变。
