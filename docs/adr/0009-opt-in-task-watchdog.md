# 0009：任务看门狗采用显式登记，由 status 统一编排

状态：已接受并实施，完整回归和当前固件构建通过；实板验证未执行。见[正式规格](../../.scratch/task-watchdog/spec.md)、[当前验证](../../.scratch/task-watchdog/application-timer.md)与[多任务看门狗方案](../task-watchdog.md)。

各任务自行登记允许的最大心跳间隔，`status` 调用底层能力管理监控和外部喂狗；
只对活动登记项应用期限，没有活动登记项且无锁存故障时持续喂狗，不检查未登记的应启动任务。
普通休眠计入预算，显式永久休眠退出监控、恢复时重新登记；任一超时先锁存 RAM 故障并停止外部喂狗，再请求软件复位。
诊断不跨重启保存，当前主循环、DP、CO、TR、IAP 暂不接入，后续由用户逐项增加。

这一选择将监控覆盖范围交给显式业务编排，避免正常空闲或有意停用被认作故障；
相应地，未登记任务不获得新增时限保护。旧隐式主循环/DP 活性超时已解除，不再作为未登记任务的看门狗约束。
该部分替代既有健康策略中的隐式活性检查；ADR 0007 的任务归属和 ADR 0008 的远端离线不停止整机喂狗继续有效。

## 实施后的依赖修正

用户明确要求任务超时逻辑留在应用层，不增加 `CONFIG_TASK_WDT*` 配置。
现由 `app/status/task_watchdog/` 维护活动任务链表和单个 Zephyr 内核定时器，
登记上下文由调用者持有，无固定通道数组、容量配置或堆分配。
定时器跟踪最早期限；全部永久休眠时停止检查定时器，外部 GPIO 喂狗继续。
原采用 Zephyr Task Watchdog 子系统及手动配置通道容量的决定被本次修正替代；
公开接口、终止故障、RAM 诊断及现有任务暂不接入的边界保持。
