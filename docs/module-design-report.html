1 项目概述

项目目标是以 Zephyr 承接原平台能力，逐步形成源码可维护、模块可测试、 产品可配置的实现。当前重点是完成底层通用能力与产品代码的边界收敛。

01 · 数据统一

业务围绕测点运行

DP 管理设备和点值，提供统一读写、回调、范围校验与参数保存。 采样和通信通过测点交互，减少直接耦合。

02 · 通信分层

端口、协议、映射分开

vport 交付字节事件，transmit 管理协议选择与测点映射， Modbus 模块复用 Zephyr 服务端；APP 管理物理串口与线程。

03 · 保障独立

监控与升级模块化

watchdog 管理健康检查与硬件喂狗，IAP 管理接收、解包、验签与升级。 产品状态和显示策略由 APP 维护。

实现情况：通用模块已在 IDU-pre 中装配运行，具备独立测试与组合测试； 已完成 MCUboot + IAPv3 固件构建、签名验证和 SGZ 导出。完整旧平台功能替代仍在推进。

3 通用模块设计

本章按模块职责、数据模型、处理流程、接口约束和调用方式说明通用模块设计。模块名称与当前代码目录保持一致。

各模块分别说明设计方案、对外接口与调用示例，完整类型与函数声明以模块公开头文件为准。 DP → vport → transmit 三段示例构成连续集成流程，其余示例分别说明独立调用方式。 调用示例用于说明接口集成方式；产品适配函数由 APP 实现，示例不计入已交付功能。

3.1 common — 公共数值基础

已实现

让 DP 和通信模块共用一套类型与计算规则，避免各模块重复定义和转换。

设计方案

共享类型放在 common，其他模块只依赖基础库，无需为使用数值联合体引入 DP 依赖。类型标识由接口显式传递，避免根据联合体内容猜类型。

数值转换和协议编解码分开：value_convert 处理本机数值语义，寄存器大端字节、CRC 等归 Modbus。

对外接口

接口作用与调用约束
value_can_convert(source_type, target_type)先判断组合是否支持，不运行回调。
value_convert(source_type, source, target_type, target)复制或转换 value_t；允许原地转换，失败不修改目标。
value_integer_bits / get / from_bits分别取得位宽、提取 int64 数值、按低位构造整数；供通用计算和编码使用。
value_storage_type(type)获得稳定存储类型编号；非法类型返回 0，不将枚举数字直接当作存储格式。
value_scale_apply(scale, inverse, input, output)inverse=false 正向；true 逆向。成功返回 0，零分子/分母或中间溢出返回负值。

调用示例

#include <common/value.h>
#include <common/scale.h>

int common_example(void)
{
    value_t source = {.u32 = 100000};
    value_t external = {0};
    int err = value_convert(VALUE_TYPE_U32, &source,
        VALUE_TYPE_U16, &external);
    if (err) {
        return err;
    }
    /* 收窄后 external.u16 为 34464。 */
    static const value_scale_t scale = {
        .numerator = 1,
        .denominator = 100,
        .offset = 0,
    };
    int64_t output = 0;
    err = value_scale_apply(&scale, false, external.u16, &output);
    if (err) {
        return err;
    }
    /* output 为 344：先收窄，再除以 100。 */
    return output == 344 ? 0 : -1;
}

该示例用于说明数值转换与放缩规则，无硬件依赖。调用者始终初始化整个 value_t，并按声明类型访问对应成员。

接口：value_convert()、value_scale_apply() · 设计说明

3.2 dataprocess — 测点与参数中心

已实现 / 含持久化

统一设备数据模型，使采样、参数操作和通信访问使用同一个数据入口。

dp_init→登记设备 / 校验点表 / 加载参数 →业务 set / get→脏点延后写入 NVS
保存语义：set 成功表示 RAM 更新成功，不能等同于 Flash 已保存。 掉电可能丢失尚未落盘的修改；主动重启前需要停止修改并 flush。 存储布局不匹配会按当前策略清空总参数区并重建，版本发布须管理布局变更。

设计方案

将配置和运行值分离：只读点表由应用常驻持有，DP 分配私有运行数据。同一配置可登记给多个设备，点值互不共享。

key 与 index 分工：key 是持久记录的稳定身份，点表重排不应改变 key；index 是当前表的行下标，使用枚举和指定下标初始化，便于直接定位。

对外接口

接口作用与调用约束
dp_init(void)线程调用；初始化总存储布局与保存线程；成功后可重复调用。
dp_register_device(device_id, table)登记并加载持久值；device_id 非零且唯一。表行常驻；不能与业务访问并发。
dp_set_para_by_key(device_id, signal_key, input_type, value)按稳定 key 写入；转换→写回调→范围校验→RAM；返回 0 不代表落盘。
dp_get_para_by_key(device_id, signal_key, output_type, value)按 key 读取；读回调使用内部类型，之后转换输出；失败保持输出不变。
dp_set_para_by_index(device_id, signal_index, input_type, value)按枚举行下标写入；索引从 0 开始，越界 -ENOENT。
dp_get_para_by_index(device_id, signal_index, output_type, value)按枚举行下标读取；与按 key 访问同一个点。
dp_flush(void)线程同步保存当前脏点；并发新修改未必包含在本轮，保证落盘前须停止修改。
dp_restore_defaults(device_id)恢复 RAM 初值、标记持久点待保存；跳过 SKIP_DEFAULTS，不调用业务回调。
dp_factory_reset(device_id, before_reboot, context)删除 Flash 后执行可选回调并冷重启；成功不返回。ALL=0 仅在本接口表示所有设备。
dp_remove_device(device_id)永久删除设备 Flash、索引和私有 RAM；不存在返回 0；调用前等待全部业务静止。

调用示例

#include <dataprocess/dataprocess.h>
#include <zephyr/sys/util.h>
#include <errno.h>

/* 示例身份可与后文 transmit 的映射配置组合使用。 */
typedef enum {
    DEMO_DEVICE = 1,
} demo_device_t;
typedef enum {
    DEMO_PERIOD,
    DEMO_POINT_COUNT,
} demo_index_t;
typedef enum {
    DEMO_PERIOD_KEY = 100,
} demo_key_t;

static int period_write(const dp_callback_context_t *context)
{
    /* context 同时提供 device_id、signal_key、signal_index、is_write。
     * 此处 value 为点表内部 U16，可校正值；副作用不要依赖回滚。
     */
    return context->value->u16 % 10 == 0 ? 0 : -EINVAL;
}

static const dp_point_config_t demo_points[DEMO_POINT_COUNT] = {
    [DEMO_PERIOD] = {
        .signal_key = DEMO_PERIOD_KEY,
        .size = 2,
        .flags = DP_POINT_FLAG_PERSISTENT | DP_POINT_FLAG_CHECK_RANGE,
        .type = VALUE_TYPE_U16,
        .write_callback = period_write,
        .read_callback = NULL,
        .data = {
            .initial = {.u16 = 500},
            .minimum = {.u16 = 100},
            .maximum = {.u16 = 1000},
        },
    },
};
static const dp_table_t demo_table = {
    .points = demo_points,
    .point_count = ARRAY_SIZE(demo_points),
};

int demo_dp_start(void)
{
    int err = dp_init();
    if (err) {
        return err;
    }
    return dp_register_device(DEMO_DEVICE, &demo_table);
}

int demo_dp_update(void)
{
    value_t input = {.u16 = 600};
    int err = dp_set_para_by_key(DEMO_DEVICE, DEMO_PERIOD_KEY,
        VALUE_TYPE_U16, &input);
    if (err) {
        return err;
    }
    value_t output = {0};
    /* 同一个点：按 key 写，按 index 以 U32 读。 */
    err = dp_get_para_by_index(DEMO_DEVICE, DEMO_PERIOD,
        VALUE_TYPE_U32, &output);
    if (err) {
        return err;
    }
    /* 业务正常运行时无需每次 set 都 flush，由后台合并保存。
     * 主动重启前应先停止所有参数修改，再调用 dp_flush()。
     */
    return output.u32 == 600 ? 0 : -EIO;
}

前提：CONFIG_DATAPROCESS=y，DTS 存在 dp-params 别名且容量满足槽位要求。示例的设备、key、index 仅用于示例，不替换产品表。所有 DP 业务入口在线程上下文调用。

接口：dp_init、dp_register_device、 dp_*_para_by_key/index、dp_flush、恢复与删除接口 · 设计说明

3.3 vport — 统一端口接入

已实现

以相同方式交付不同物理端口的数据，协议模块无需操作具体 UART 和 GPIO。

设计方案

端口对象仅保存发送回调和唯一接收者，不维护全局设备目录。端口对象由 APP 持有，减少模块全局状态。

交付字节与事件而非完整报文，使流式协议和 RTU 都能在同一接入抽象上工作。实际帧边界由具体协议判断。

对外接口

接口作用与调用约束
vport_bind(port, receive, context)启动时绑定唯一接收者；transmit 注册时内部调用，APP 不再重复绑定。
vport_input(port, event)线程同步交付 DATA / IDLE / POLL / ERROR；同一端口由 APP 串行调用。
vport_output(port, data, size, timeout)同步转给 APP 的发送回调；禁止回调保留 data；正返回归一为 -EIO。
vport_send_t / vport_receive_t发送和接收回调类型；context 区分物理端口或上层实例。

调用示例

#include <vport/vport.h>

/* 由产品物理层实现：含方向控制、发送完成等待和超时中止。 */
int app_uart_send(const uint8_t *data, size_t size, k_timeout_t timeout);

static int demo_send(void *context, const uint8_t *data,
    size_t size, k_timeout_t timeout)
{
    ARG_UNUSED(context);
    return app_uart_send(data, size, timeout);
}

static vport_t demo_port = {
    .send = demo_send,
    .send_context = NULL,
};

/* 由唯一 APP 接收线程调用；rx_us 来自硬件接收时间。 */
int demo_deliver_byte(uint8_t byte, uint64_t rx_us)
{
    vport_event_t event = {
        .type = VPORT_DATA,
        .data = &byte,
        .size = 1,
        .at_us = rx_us,
    };
    return vport_input(&demo_port, &event);
}

/* 确认更早数据已经出队后，用当前单调时间推进超时。 */
int demo_poll(uint64_t now_us)
{
    vport_event_t event = {
        .type = VPORT_POLL,
        .at_us = now_us,
    };
    return vport_input(&demo_port, &event);
}

此片段与下文 transmit 共用 demo_port。APP 先设置发送回调，tr_register 成功后再启动接收。app_uart_send 是产品适配入口，不是模块自带 API。

接口：vport_bind/input/output · 设计说明

3.4 transmit — 对外从机协议与测点映射

已实现 / 产品接入 Modbus

把协议访问转换为 DP 操作，维护协议选择、接收缓存和对外数据表达。

当前明确的数据换算顺序

读：DP 原值→转换为对外类型→ 正向放缩→协议编码
写：协议解码→逆向放缩 →按对外类型表示→DP 转换 / 回调 / 校验

先转换后放缩可能先丢失高位，这是当前约定；整数收窄不做饱和。 scale 指针为空直接跳过计算。业务表需保证所选类型满足数值精度要求。

设计方案

实例将端口、协议顺序和缓存容量一起登记，成功后配置不变。所有权在启动时确定，运行期不需要动态注册或缓存申请。

识别与执行分两步：check 只检查缓存视图，返回 WAIT / MISMATCH / COMPLETE；execute 只在完整报文被选中后运行一次，避免探测阶段触发写入。

对外接口

接口作用与调用约束
tr_register(const tr_config_t *config)唯一公开函数：检查配置、申请缓存、占用 RAW 接口并绑定 vport；失败回收本次资源。
tr_config_tport、protocols、protocol_count、rx_capacity、tx_capacity、send_timeout_ms。配置及引用对象常驻。
tr_protocol_ttype、max_frame、timeout_us，及 Modbus 配置或 CUSTOM 的 check / execute / context。每类最多一个。
tr_modbus_point_t / tr_mapping_t协议侧 area/address/count/word_order，内部侧设备/index/对外类型/可选 scale。
tr_check_t / tr_execute_tCUSTOM 回调：检查无副作用；COMPLETE 必须给出消费长度，execute 给出回复长度，0 长度为静默。
tr_modbus_route_taddress/count 保留请求起始地址范围，callback 处理完整 ADU；命中错误不回退普通测点。

调用示例

#include <transmit/transmit.h>
#include <zephyr/sys/util.h>

/* 与上文 DP、vport 片段处于同一集成示例中。 */
static const value_scale_t period_scale = {
    .numerator = 100,
    .denominator = 1,
    .offset = 0,
};
static const tr_modbus_point_t demo_forward[] = {
    {
        .area = MB_DATA_AREA_HOLDING_REGISTER,
        .address = 0,
        .count = 2,
        .word_order = MB_HIGH_WORD_FIRST,
        .mapping = {
            .device_id = DEMO_DEVICE,
            .signal_index = DEMO_PERIOD,
            .external_type = VALUE_TYPE_U32,
            .scale = &period_scale,
        },
    },
};
static const tr_protocol_t demo_protocols[] = {
    {
        .type = TR_PROTOCOL_MODBUS,
        .max_frame = 256,
        .timeout_us = 500000,
        .modbus = {
            .unit = 1,
            .gap_us = 1750, /* 本例假设 115200 8N1。 */
            .points = demo_forward,
            .point_count = ARRAY_SIZE(demo_forward),
            .routes = NULL,
            .route_count = 0,
        },
    },
};
static const tr_config_t demo_transmit = {
    .port = &demo_port,
    .protocols = demo_protocols,
    .protocol_count = ARRAY_SIZE(demo_protocols),
    .rx_capacity = 256,
    .tx_capacity = 256,
    .send_timeout_ms = 100,
};

int demo_protocol_start(void)
{
    int err = demo_dp_start();
    if (err) {
        return err;
    }
    /* 成功后 APP 才开放物理 RX，串行调用 demo_deliver_byte / demo_poll。 */
    return tr_register(&demo_transmit);
}
/* DP 周期 600 时，03 读地址 0、数量 2 得到 U32 的 60000。
 * 16 写这两个寄存器为 50000，逆放缩得到 DP 的 500。
 * 写单个寄存器只覆盖该点一半，按当前规则拒绝。
 */

依赖 CONFIG_TRANSMIT、Zephyr MODBUS_SERVER / RAW 及足够堆预算。这里只配置普通短帧；接入 IAP 必须扩大 max_frame、rx_capacity、MODBUS_BUFFER_SIZE 和堆预算，参照产品真实配置。

3.5 modbus — 标准协议能力与 Zephyr 适配

已实现 / 固定版本适配

复用 Zephyr 标准功能码处理，补齐适合当前同步模块架构的接口。

版本维护成本：兼容脚本校验 Zephyr v4.5.0 源文件哈希和替换位置。 升级 Zephyr 时必须重新审查并验证，不能直接沿用同步扩展和协议修复。

Zephyr 4.5.0 适配内容

上游变化当前处理验证方式
新增 modbus_work_submit 与可选专用队列自有 RAW 进入同步钩子；其他接口回到官方投递入口，保留队列选择默认队列与专用队列分别执行，检查实际处理线程
RAW 缓冲区长度上限已修复直接使用上游 sizeof(data) 检查，移除旧版重复替换正常、畸形长度与客户端异常响应回归
串口中断与异步关闭流程更新以 4.5.0 串口源码生成构建副本，保留现有接入扩展生成锚点检查；当前产品 UART/GPIO 模拟接入回归
服务端功能码文件与 4.4.2 相同继续保留高地址读取、非法线圈值、数量与响应容量等边界修复功能码、寄存器数量、整笔访问和异常响应验证
源码版本变化更新经审查的源码哈希，继续严格校验，不允许未知源码进入适配修改源码副本的探针被拒绝

CONFIG_MODBUS_WORKQUEUE 仅影响官方异步路径；当前产品默认不创建此专用队列。 启用该配置的测试变体验证了兼容性，但不改变 APP 协议线程同步调用业务回调的归属。 本次没有修改公开 API、点表配置、参数格式或 Flash 布局。

设计方案

把标准功能码实现交给 Zephyr，项目维护同步适配和接口上下文。这样可独立测试协议层，不需要启动 DP。

官方按寄存器/位调用的回调，经适配器合并成一次 mb_request_t 整笔访问。业务后端可预检全部数据，避免逐寄存器重复读取同一点。

对外接口

接口作用与调用约束
mb_server_open(unit, &server)启动期占用 RAW 接口；不足返回 -ENOSPC。
mb_server_process(server, request, response, &respond, access, context)同步处理完整 ADU；返回后根据 respond 决定是否发送，广播写不回复。
mb_server_close(server)仅启动失败回退使用；正在处理时 -EBUSY，不作为运行期动态重配方案。
mb_access_t(context, request)整笔访问回调返回 0 或正 Modbus 异常码；负值归一为设备故障。寄存器数据为大端字节。
mb_rtu_validate / decode / encode完整 RTU 长度/CRC 检查、RTU→ADU、ADU→RTU；无动态分配。
mb_rtu_probe(...)根据边界、损坏与过期标志检查缓存；等待 -EAGAIN，不匹配 -EBADMSG，成功给出帧长。
mb_register_value / mb_decode_value在调用方已校验类型、容量和范围的前提下处理寄存器字序。
transport.h 中 mb_serial_* / mb_client_* / mb_raw_set_done保留的传输与客户端扩展，当前产品从机链路不使用；不表示南向 collect 已恢复。完整声明见模块公开头文件。

调用示例

#include <modbus_support/server.h>
#include <modbus_support/rtu.h>
#include <zephyr/sys/byteorder.h>

static mb_server_t *demo_server;
static uint16_t holding;

static int access_register(void *context, const mb_request_t *request)
{
    ARG_UNUSED(context);
    if (request->area != MB_DATA_AREA_HOLDING_REGISTER ||
        request->first != 0 || request->count != 1) {
        return 2; /* Modbus 异常 02：非法地址。 */
    }
    if (request->writing) {
        holding = sys_get_be16(request->data);
    } else {
        sys_put_be16(holding, request->data);
    }
    return 0;
}

int demo_mb_open(void)
{
    return mb_server_open(1, &demo_server);
}

int demo_mb_handle(const uint8_t *frame, size_t size,
    uint8_t *output, size_t capacity, size_t *output_size)
{
    struct modbus_adu request = {0};
    struct modbus_adu response = {0};
    *output_size = 0;
    int err = mb_rtu_decode(frame, size, &request);
    if (err) {
        return err;
    }
    bool respond = false;
    err = mb_server_process(demo_server, &request, &response,
        &respond, access_register, NULL);
    if (err || !respond) {
        return err;
    }
    return mb_rtu_encode(&response, output, capacity, output_size);
}

这是不依赖 DP / transmit 的独立服务端用法，与前面的 transmit 示例二选一，不能抢占同一个 RAW 槽位。调用方保证完整帧、参数非空、实例串行及发送完成；正式产品无需自行再调用此链路。

接口：mb_server_*、mb_rtu_* 与寄存器转换 · 设计说明

3.6 watchdog — 任务健康与硬件喂狗

已实现

将任务监控、健康有效期和外部喂狗统一管理，应用不感知喂狗引脚。

任务报告进展→workqueue 完整检查 →发布健康期限→k_timer 决定硬件喂狗

工作队列阻塞时，由健康过期和外部芯片兜底；关闭外部喂狗后不具备同等保障。 终止故障只能通过重启重新初始化，可恢复通信异常应由业务自行处理。

设计方案

任务进展不直接触发硬件喂狗。只有软件完整扫描通过，才发布可用健康结论，防止单个活跃任务掩盖其他任务卡死。

扫描在 workqueue，硬件边沿在 k_timer。硬件定时器不获取任务列表锁，避免依赖工作队列实时执行；三倍有效期给正常调度留出余量。

对外接口

接口作用与调用约束
watchdog_init(notify)线程显式初始化；每次上电只尝试一次，唯一 notify 必须非空；初始化失败直接返回。
watchdog_task_register(task, config)常驻且首次清零的任务对象；复制配置，名称常驻；线程调用。
watchdog_task_feed(task)报告真实进展；迟到返回 -ETIMEDOUT 并锁存，不应只为喂狗而虚假报告。
watchdog_task_sleep_forever(task)退出期限监控，不会使线程真正休眠；重新监控须登记。
watchdog_report_fault(error, description, action, reset_delay_ms)线程 / ISR 可用，描述常驻且 error 非零；RESET 使用毫秒延时，0 立即复位，上限 60 秒。
watchdog_stop(mode)非阻塞停止检查或全部停止；本次启动不能重新启用，不取消既有复位。
watchdog_task_get / watchdog_fault_get复制诊断快照，不处理通知或恢复状态；无记录 -ENOENT。
watchdog_fault_cb_t(snapshot)唯一只读回调；主动上报可从 ISR 同步进入，必须非阻塞、ISR 安全，不递归上报。

调用示例

#include <watchdog/watchdog.h>
#include <zephyr/sys/atomic.h>

static struct watchdog_task sample_task;
static atomic_t business_stopped;

static int fault_notify(const struct watchdog_fault *fault)
{
    /* 仅执行 ISR 安全的状态发布；不阻塞、不递归 report。 */
    if (fault->action != WATCHDOG_ACTION_CONTINUE) {
        atomic_set(&business_stopped, 1);
    }
    return 0;
}

int demo_watchdog_start(void)
{
    int err = watchdog_init(fault_notify);
    if (err) {
        return err;
    }
    const struct watchdog_task_config config = {
        .name = "sample",
        .timeout_ms = 1000,
    };
    return watchdog_task_register(&sample_task, &config);
}

int demo_sample_done(void)
{
    /* 完成一次真实采样后，由对应任务调用。 */
    return watchdog_task_feed(&sample_task);
}

int demo_terminal_fault(int error)
{
    return watchdog_report_fault(error, "Sample pipeline failed",
        WATCHDOG_ACTION_RESET, 200);
}

该例展示独立接入模式。当前产品已在 status_init 内完成 watchdog_init 和回调绑定，不能再次调用 demo_watchdog_start。business_stopped 只是示例门禁，APP 必须在业务入口读取它才会停止业务。

入口：watchdog_init、任务登记/心跳、 watchdog_report_fault、诊断查询 · 设计说明

3.7 iap — 兼容旧协议的在线升级

已接入 / 实板互通待验

兼容旧 IAPv3 / SGZ 接收方式，使用 MCUboot 完成签名镜像升级。

尚待闭环：默认升级流程没有接入 DP 冻结与 flush 钩子， 升级重启可能丢失尚未保存的参数。需要通过 prepare_reboot / cancel_reboot 配对钩子完成应用协调。

设计方案

接收与镜像处理解耦：Modbus 回调校验和提交任务，专用线程完成耗时擦写、解密、解包和验签，减少协议调用被 Flash 长操作占用。

传输兼容与可信启动分开：旧 AES 用于传输互操作，不能证明固件可信；最终使用 P-256 验签和 MCUboot 试运行机制。

对外接口

接口作用与调用约束
iap_init(void)CONFIG_IAP_CONFIGURED 模式，从 DTS / Kconfig 与生成密钥显式初始化；先于安装路由。
iap_init_config(config)显式配置暂存/日志分区、AES、公钥策略和配对回调；配置复制，密钥和 context 常驻。与 iap_init 二选一。
iap_ready(void)查询接收器是否就绪。
iap_route(iface, request, response)完整 ADU 路由；0 回复，IAP_ROUTE_SILENT 消费不回复，-ENOENT 不归本模块；iface 非负。
iap_stop(void)线程 / ISR 可用；终止状态保持到复位，当前 Flash 操作安全完成，已准入提交不回滚。
iap_sgz_crc32 / iap_sgz_decrypt容器校验和与原地 AES 解密辅助接口。
iap_sgz_unpack(read, in, received, max_image_size, write, out, ws, image_size)读写回调式有界解包，调用方提供工作区和输入/输出上限。
iap_image_verify(read, context, available, policy, hash)按地址、SRAM、长度及公钥策略校验 MCUboot 镜像并输出哈希。

调用示例

#include <iap/iap.h>
#include <transmit/transmit.h>

{

}

    {.address = 20003, .count = 1, .callback = upgrade_access},
    {.address = 20049, .count = 56, .callback = upgrade_access},
    {.address = 31996, .count = 2, .callback = upgrade_access},
};

int demo_iap_start(void)
{
    /* 当前产品使用的配置式初始化；之后再登记带 routes 的实例。 */

}
/* tr_protocol_t.modbus.routes = upgrade_routes;
 * tr_protocol_t.modbus.route_count = ARRAY_SIZE(upgrade_routes);

 */

产品 forward.c 已使用此路由方式，不应重复注册。路由只匹配请求起始地址，count 不是上传载荷数量上限。CRC 与站号由 transmit 过滤，功能码/载荷/会话由 IAP 校验；此例不包含尚待落实的 DP 保存门禁。

3.8 quicklz — 解压算法支撑

设计方案

算法接口只处理一个完整块，不保留跨块历史，不需要线程、堆和端口。输入/输出由调用者控制，便于主机验证。

输入格式错误和输出空间不足统一返回 -EBADMSG；成功返回实际字节数。失败不保证目标内容，因此应在成功后才消费输出。

对外接口

接口作用与调用约束
qlz_decode_level3(src, len, dst, cap)QuickLZ 1.5 level 3 完整块解码；缓冲不可重叠，cap 必须能用 int 表示。

调用示例

#include <quicklz/quicklz.h>

int demo_decode_block(const uint8_t *compressed, size_t compressed_size,
    uint8_t *plain, size_t plain_capacity)
{
    int size = qlz_decode_level3(compressed, compressed_size,
        plain, plain_capacity);
    if (size < 0) {
        return size;
    }
    /* 仅在成功后消费 plain[0..size)，不能假设总是填满缓冲。 */
    return size;
}

compressed 必须是完整合法块，不能直接传未解密 SGZ 容器。IAP 已处理容器与工作区，产品业务通常不直接调用解压函数。

3.9 gd32e505 — 硬件平台适配

设计方案

以 Zephyr 模块的 soc_root / dts_root 提供缺失的芯片描述与绑定，硬件配置由 DTS 生成，避免应用包含厂商初始化代码。

应用和 MCUboot 通过同一硬件模块获得时钟来源。20 MHz 有源旁路、PLL /5×45 等配置在构建时做约束检查。

对外接口

接口作用与调用约束
模块接入：ZEPHYR_EXTRA_MODULES / hardware.cmakefind_package(Zephyr) 前登记；不是应用运行期 API。SoC 和 ADC 由标准设备初始化机制启动。
adc_is_ready_dt(spec)Zephyr 官方就绪检查，确认底层设备可用。
adc_channel_setup_dt(spec)Zephyr 官方通道配置接口，设置引脚对应通道、增益、参考等；应用读取前调用。
adc_sequence_init_dt(spec, sequence)Zephyr 官方辅助接口，从通道描述填写 sequence 的通道、分辨率、过采样配置。
adc_read_dt(spec, sequence)Zephyr 官方同步采样；E505 后端目前只支持单通道。GPIO 继续使用官方 gpio_* 接口。

调用示例

#include <zephyr/drivers/adc.h>
#include <errno.h>

/* 使用当前板 idu_io 的命名通道，不依赖通道在数组中的位置。 */
static const struct adc_dt_spec current =
    ADC_DT_SPEC_GET_BY_NAME(DT_NODELABEL(idu_io), current_1);

int demo_adc_read(int16_t *raw)
{
    if (!adc_is_ready_dt(&current)) {
        return -ENODEV;
    }
    int err = adc_channel_setup_dt(&current);
    if (err) {
        return err;
    }
    struct adc_sequence sequence = {
        .buffer = raw,
        .buffer_size = sizeof(*raw),
    };
    err = adc_sequence_init_dt(&current, &sequence);
    if (err) {
        return err;
    }
    return adc_read_dt(&current, &sequence);
}

示例返回原始 ADC 数值。正式产品在启动时 setup 一次、周期内重复读取，并在 acquisition 中完成平均和工程量换算。通道引用依赖当前板 DTS。该模块没有自定义的 gd32_* 产品 API。

4 产品集成方案

本地数据链路

ADC / GPIO→acquisition →DP 测点

APP 按硬件映射读取 16 路 DI 和 8 路 AI。DI 作为位图测点，AI 各自写入独立测点， 工程量换算归产品采样逻辑。此处是本地采样，不代表南向 Modbus 采集已恢复。

对外通信链路

RS485-1→vport→ transmit→Modbus / DP 或 IAP

protocol.c 装配站号、转发表与升级路由，创建协议线程；rs485_1.c 仅提供物理事件与发送回调。 标准读写进入 DP，升级报文进入 IAP。

产品复用方案：新产品保留通用模块，主要提供板级 DTS、 内部点表、协议映射表和 APP 端口接入。扩展新协议或芯片时，仍需增加相应适配代码与测试。
