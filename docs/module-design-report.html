基于 Zephyr 的通用模块设计

以 IDU-pre 为首个落地产品，将测点数据、协议转发、任务监控和在线升级沉淀为可复用模块， 为后续多设备、多产品开发建立统一基础。

代码基线：6faba2fZephyr：v4.4.2 阶段：核心实现与模拟验证，推进实板验收

01 / OVERVIEW总体介绍：从单板业务走向可复用能力

项目目标是以 Zephyr 承接原平台能力，逐步形成源码可维护、模块可测试、 产品可配置的实现。当前重点是完成底层通用能力与产品代码的边界收敛。

01 · 数据统一

业务围绕测点运行

DP 管理设备和点值，提供统一读写、回调、范围校验与参数保存。 采样和通信通过测点交互，减少直接耦合。

02 · 通信分层

端口、协议、映射分开

vport 交付字节事件，transmit 管理协议选择与测点映射， Modbus 模块复用 Zephyr 服务端；APP 管理物理串口与线程。

03 · 保障独立

监控与升级模块化

watchdog 管理健康检查与硬件喂狗，IAP 管理接收、解包、验签与升级。 产品状态和显示策略由 APP 维护。

当前成果：通用模块已在 IDU-pre 中装配运行，具备独立测试与组合测试； 已完成 MCUboot + IAPv3 固件构建、签名验证和 SGZ 导出。完整旧平台功能替代仍在推进。

03 / MODULES各通用模块设计

按“解决什么问题、如何实现、边界在哪里”介绍。模块名称与当前代码目录保持一致。

01 · common — 公共数值基础

已实现

让 DP 和通信模块共用一套类型与计算规则，避免各模块重复定义和转换。

核心设计
value_t 联合体 + value_type_t 类型标识； 类型转换和比例偏移计算分别提供公共函数。
类型转换
U8、U16、S16、U32、S32 相互转换；收窄保留低位，按补码解释符号。 STRING、BYTES、WORDS 仅支持同类型复制。
放缩规则
输出 = 输入 × 分子 ÷ 分母 + 偏移；逆向用于写入。 int64 中间计算、整数除法向零取整、计算溢出返回错误。
职责边界
不理解设备、测点、Modbus 字序或硬件。联合体中的浮点视图不代表系统已支持浮点测点。

接口：value_convert()、value_scale_apply() · 设计说明

02 · dataprocess — 测点与参数中心

已实现 / 含持久化

统一设备数据模型，使采样、参数操作和通信访问使用同一个数据入口。

设备与点表
APP 提供常驻只读点表，DP 私有维护设备目录和运行值。 device_id 区分设备；signal_key 是稳定标识；signal_index 是枚举表示的点表行下标。
读写流程
支持 key / index 四个显式类型读写接口。写入先转换为内部类型，再回调、范围校验、更新 RAM。 读回调可更新点值；业务回调始终使用内部类型。
参数保存
DTS 指定 dp-params 总分区，内部划分管理区与设备槽位。 每持久测点一条 NVS 记录，以 key 定位；修改一个点无需重写整台设备。
后台与并发
独立线程默认每次等待 5 秒后扫描脏点。保存副本用于判断是否需要落盘； Flash 操作不持有点值锁。dp_flush() 提供同步保存。
恢复与删除
恢复默认值更新 RAM 并标脏；出厂恢复擦除目标设备参数后重启，支持全部设备。 删除设备还会释放其私有 RAM。登记、删除须由 APP 管理业务静止期。
dp_init→登记设备 / 校验点表 / 加载参数 →业务 set / get→脏点延后写入 NVS
保存语义：set 成功表示 RAM 更新成功，不能等同于 Flash 已保存。 掉电可能丢失尚未落盘的修改；主动重启前需要停止修改并 flush。 存储布局不匹配会按当前策略清空总参数区并重建，版本发布须管理布局变更。

接口：dp_init、dp_register_device、 dp_*_para_by_key/index、dp_flush、恢复与删除接口 · 设计说明 · 存储决策

03 · vport — 统一端口接入

已实现

以相同方式交付不同物理端口的数据，协议模块无需操作具体 UART 和 GPIO。

接收形式
统一 DATA、IDLE、POLL、ERROR 事件，携带单调微秒时间戳。 支持单字节或字节块，不要求接入层先拼完整报文。
发送形式
通过 APP 绑定的同步带超时发送回调输出；返回前完成或中止发送，不保留借用数据指针。
职责边界
不创建线程、不判帧、不解释 CAN ID。APP 负责 CAN 分流/重组、共享总线仲裁和同端口串行交付。

接口：vport_bind/input/output · 设计说明

04 · transmit — 对外从机协议与测点映射

已实现 / 产品接入 Modbus

把协议访问转换为 DP 操作，维护协议选择、接收缓存和对外数据表达。

实例模型
一个实例绑定一个 vport，每类协议最多一个；目前支持内置 Modbus RTU 与 CUSTOM 接入项。 APP 可登记多个实例；产品当前使用一个 Modbus 从机入口。
报文识别
transmit 保存未消费数据。候选协议等待时保持锁定，明确不匹配才环形切换； 候选从共同起点检查，协议检查不直接删除缓存。POLL 推进静默判帧和超时。
转发表
协议行配置地址、长度、数据区和字序；通用 mapping 内嵌设备、点 index、对外类型和可选放缩。 内部点表与对外地址表相互独立。
扩展入口
完整 ADU 地址段回调可接入 IAPv3。 在标准功能码数量校验前分派，避免旧超长 FC16 被标准限制拒绝；命中后不回退普通测点。
资源与边界
启动时分配固定接收/发送缓存，运行期不分配；不创建线程。 多点写首错停止且不回滚；发送失败不自动重放业务。新增内置协议仍需修改分派代码。

当前明确的数据换算顺序

读：DP 原值→转换为对外类型→ 正向放缩→协议编码
写：协议解码→逆向放缩 →按对外类型表示→DP 转换 / 回调 / 校验

先转换后放缩可能先丢失高位，这是当前约定；整数收窄不做饱和。 scale 指针为空直接跳过计算。业务表需保证所选类型满足数值精度要求。

入口：tr_register() · 设计说明 · 完整通信方案

05 · modbus — 标准协议能力与 Zephyr 适配

已实现 / 固定版本适配

复用 Zephyr 标准功能码处理，补齐适合当前同步模块架构的接口。

官方能力
使用 Zephyr RAW 服务端处理 01/02/03/04/05/06/15/16 的分派、数量校验、位打包和正常/异常响应。
项目补充
提供 RTU 判帧与 CRC 编解码、公共寄存器字序转换、实例上下文，以及每请求一次的整笔访问回调。
同步方式
官方 RAW 默认异步。当前通过受控构建副本扩展，使本适配器拥有的 RAW 接口在 APP 调用线程执行； 其他 RAW 接口保持官方行为。不修改 west 依赖源码。
职责边界
不依赖 DP 或产品点表。协议地址对应哪个测点、如何放缩由 transmit 负责。 RAW 不接收 UART 字节，不能替代物理接入与 RTU 边界判断。
版本维护成本：兼容脚本校验 Zephyr v4.4.2 源文件哈希和替换位置。 升级 Zephyr 时必须重新审查并验证，不能直接沿用同步扩展和协议修复。

接口：mb_server_*、mb_rtu_* 与寄存器转换 · 设计说明

06 · watchdog — 任务健康与硬件喂狗

已实现

将任务监控、健康有效期和外部喂狗统一管理，应用不感知喂狗引脚。

健康检查
系统 workqueue 周期检查登记任务，软件监控随模块启用。 成功检查生成有效期，固定为软件检查周期的 3 倍；任务心跳本身不续期健康结论。
硬件喂狗
周期 k_timer 只读取原子状态和健康截止时间、翻转 GPIO，脱离任务共享锁。 本轮先按已有健康状态喂狗，再检查过期；过期后下一轮停止喂狗。
故障动作
统一 report 接口携带错误、描述、动作与复位延时。 HOLD 停业务、停检查并保留可用喂狗；RESET 经定时器延时冷复位。 CONTINUE 仅保留诊断兼容，新产品终止故障不使用。
APP 分工
status 绑定唯一故障回调，负责业务状态和 LED；watchdog 不依赖 status。 模块仅保留最近诊断，不提供故障历史或自动恢复业务。
配置来源
DTS 绑定外部 GPIO 与喂狗周期，Kconfig 配置软件检查周期和外部喂狗启用。 调试可关闭外部喂狗，显式 RESET 仍生效。
任务报告进展→workqueue 完整检查 →发布健康期限→k_timer 决定硬件喂狗

工作队列阻塞时，由健康过期和外部芯片兜底；关闭外部喂狗后不具备同等保障。 终止故障只能通过重启重新初始化，可恢复通信异常应由业务自行处理。

入口：watchdog_init、任务登记/心跳、 watchdog_report_fault、诊断查询 · 设计说明

07 · iap — 兼容旧协议的在线升级

已接入 / 实板互通待验

兼容旧 IAPv3 / SGZ 接收方式，使用 MCUboot 完成签名镜像升级。

完整链路
Modbus ADU 接收、1 KiB 分包、重复与乱序处理、AES 解密、SGZ/QuickLZ 解包、 P-256 验签、备用槽写入、升级结果 NVS 日志和试运行请求。
后台处理
专用线程处理 Flash 擦写和解包，协议回调仅提交有界任务。 不注册串口，也不依赖 DP；入口编号用于区分上传会话归属。
产品接入
forward.c 配置三个完整 ADU 地址段，通过回调调用 iap_route()。 transmit 先完成 CRC、站号和路由判断；IAP 自行校验功能码、包长和会话。
启动与确认
显式初始化后开放路由；必要初始化成功后由 main 确认当前镜像。 MCUboot 负责启动与镜像交换，IAP 不替代 bootloader。
当前范围
单 Cortex-M 镜像、双槽 scratch 交换；不包含多镜像、差分或下挂设备升级。
尚待闭环：默认升级流程没有接入 DP 冻结与 flush 钩子， 升级重启可能丢失尚未保存的参数。需要通过 prepare_reboot / cancel_reboot 配对钩子完成应用协调。

接口：iap_init、iap_init_config、iap_route · 设计说明 · 构建与升级

04 / INTEGRATION在当前产品中如何组合运行

本地数据链路

ADC / GPIO→acquisition →DP 测点

APP 按硬件映射读取 16 路 DI 和 8 路 AI。DI 作为位图测点，AI 各自写入独立测点， 工程量换算归产品采样逻辑。此处是本地采样，不代表南向 Modbus 采集已恢复。

对外通信链路

RS485-1→vport→ transmit→Modbus / DP 或 IAP

protocol.c 装配站号、转发表与升级路由，创建协议线程；rs485_1.c 仅提供物理事件与发送回调。 标准读写进入 DP，升级报文进入 IAP。

后续复用方式：新产品保留通用模块，主要提供板级 DTS、 内部点表、协议映射表和 APP 端口接入。扩展新协议或芯片时，仍需增加相应适配代码与测试。
