# Watchdog 模块

实现集中在 `src/watchdog.c`，公开声明集中在 `include/watchdog/watchdog.h`。
应用不接触引脚、GPIO 实例或底层复位函数。模块不引用 status、协议或 IAP。

| 接口 | 作用 |
| --- | --- |
| `watchdog_init(notify)` | 每次上电只尝试一次，读取硬件配置并启动检查/喂狗 |
| `watchdog_report_fault(error, description, action, reset_delay_ms)` | 同步通知唯一回调，返回回调结果，不依赖 status |
| `watchdog_stop(mode)` | MONITOR 停止检查但保留喂狗；ALL 同时停检查和喂狗 |
| `watchdog_task_register/feed/sleep_forever` | 显式登记、报告进展、退出任务期限监控 |
| `watchdog_task_get` / `watchdog_fault_get` | 复制任务或故障诊断，不改变状态 |

删除底层多实例和 watchdog_error / watchdog_external_* / watchdog_task_monitor_* 接口。
硬件错误、任务超时和检查结果过期都通过一个故障回调报告，初始化错误直接返回。
使用 RESET 动作需应用启用 Zephyr CONFIG_REBOOT；延时使用相对超时，不依赖 CONFIG_TIMEOUT_64BIT，超过 60 秒的请求按 60 秒提前复位；关闭外部喂狗不抑制软件监控或显式复位。

## 检查、有效期与硬件喂狗

- 软件监控是模块固定能力，watchdog_init 成功后始终运行，不再提供独立开关；conf/debug.conf 只关闭外部喂狗。
- 任务检查由系统 workqueue 的 delayable work 周期执行，不创建额外线程。
- 检查周期来自 CONFIG_WATCHDOG_CHECK_INTERVAL_MS，默认 100 ms；完成检查后安排下一个周期。
- 首次检查的启动宽限与每次成功检查的有效期都固定为三倍检查周期，默认 300 ms。
- 只有完整检查通过才能续期；登记、心跳和工作开始均不续期。
- 完整扫描后验证旧健康期限；过期不能通过恢复执行自动改为健康。
- 硬件喂狗使用唯一一个周期 k_timer，只读取原子控制状态和 32 位健康截止时间并执行 GPIO 翻转，不获取任务监控共享锁。
- 定时器先按已有健康标志喂狗一次，再检查有效期；若本轮发现过期，锁存 CHECK 故障，下一周期起停止发出边沿。只提交工作，不在 ISR 中回调应用。
- 无活动任务时仍周期检查工作队列运行情况并续期；永久休眠仅移出任务列表。

任务状态与诊断快照仍由模块自旋锁保护；定时器不访问这些对象。
工作队列通过原子变量发布健康截止时间，定时器使用 32 位差值判断到期，支持时间计数正常回绕；三倍检查周期远小于半个计数范围。
定时器通过两项容量的 Zephyr 消息队列交接只读故障快照，不写共享诊断缓存。只保留一份最近诊断，事件序号保证旧的排队事件不会覆盖后来的业务上报。
只有工作队列消费故障事件并通知。诊断查询只查看最近记录和待处理事件，不消费队列、不更改模式；任务接口直接按模式判断是否允许操作。
健康续期只更新截止时间，不清除定时器锁存的异常。HOLD 关闭检查，但不能恢复已失败的 GPIO。
任务扫描在工作队列中执行，锁内扫描仍为 O(n)，大量任务时需实测其对中断延迟的影响。
没有堆分配、固定任务槽位或按到期时间重排的链表。名称和任务上下文由调用方常驻持有。
迟到心跳或退出返回 -ETIMEDOUT 并锁存异常，由工作队列通知，不能掩盖已经发生的任务超时。

## 设备树与配置

```dts
external_watchdog: external-watchdog {
    compatible = "app,gpio-watchdog";
    feed-gpios = <&gpioc 13 GPIO_ACTIVE_HIGH>;
    feed-interval-ms = <10>;
    status = "okay";
};
```

绑定由模块 dts_root 提供，外部启用时必须恰好有一个启用节点，周期大于零。
GPIO 必须是支持 ISR 安全访问的片上 GPIO。由 main → status_init → watchdog_init 显式启动，不注册 SYS_INIT。

| 外部喂狗 | 行为 |
| --- | --- |
| y | 始终执行软件检查，硬件依据模式和健康期限喂狗 |
| n | 软件检查继续执行；队列阻塞时没有外部硬件兜底，只能在恢复后发现过期 |

硬件周期只在设备树配置，软件周期只在 Kconfig 配置，有效期不单独配置。
停止控制通过同一份原子模式更新；多核上已经进入 GPIO 操作的回调允许完成，后续周期不再喂狗。实际复位还需外部芯片自身的超时时间。
系统队列中合法的长任务同样可能消耗有效期，应通过软件检查周期覆盖允许的最长阻塞。

## 故障与应用动作

### 产品终止故障约定

watchdog → status 故障通道仅用于本次启动不可恢复的故障，不提供故障清除、解除锁存或恢复业务的接口。
HOLD 停止业务、保留现场并等待人工重启；RESET 停止业务并按指定延时自动重启。
产品主线程在停止正常业务后进入留驻循环，每 5 秒查询并打印最近故障；故障上报函数与回调本身不循环，不新增打印 work。RESET 定时器不依赖该循环。
即使故障原因随后消失，也不恢复业务；重启是重新初始化的入口，不保证排除硬件损坏或配置错误等实际原因。
通信重试、远端离线重连等可恢复异常由业务模块自行维护，不通过此终止故障通道上报。

现有 CONTINUE 枚举和运行行为暂时保留用于诊断兼容，调用它仍只记录和通知、不进入终止状态，也不能解除已有锁存。
它不属于上述产品终止故障约定，新的产品故障调用只使用 HOLD 或 RESET；本次仅明确注释和文档，不删除或改变该兼容行为。
最近故障快照仅用于诊断，不表示故障已消除，也不能作为业务恢复依据。

任务超时、检查过期锁存后拒绝后续心跳，不因工作队列恢复或新心跳自动复原。
监控故障回调在系统 workqueue、模块锁外执行，快照只在回调期间有效；初始化失败不重复通知。
新的 GPIO 故障可替换此前的监控故障，用于应用已留驻后硬件喂狗失败的升级处理。

主动上报传入错误码、常驻描述、WATCHDOG_ACTION_CONTINUE / HOLD / RESET 和 uint32_t reset_delay_ms；仅动作为 RESET 时使用延时，其余动作忽略该参数。
它在调用者上下文同步通知（可以来自 ISR），不改变监控锁存故障，也不续期健康结果。
watchdog_fault_get 统一返回最近主动上报或监控故障，不保存历史。
最近故障在检测或上报时、回调之前更新，在复位前及测试复位钩子中均可查询；主动上报查询中的 action/reset_delay_ms 保留原始请求。
运行模式决定任务/喂狗许可，诊断只保存信息，普通上报覆盖最近记录不会恢复监控。待通知事件在队列中保存，消费一次即完成通知，不维护 notified 标志。
action 对主动上报表示调用方请求；内部监控故障由 watchdog 填入默认动作。参数无效或未绑定回调不覆盖记录。
回调必须非阻塞、ISR 安全、不得递归上报，并且只读：快照只在回调期间有效，不能修改任何字段。
主动上报返回回调结果，内部监控通知忽略回调返回值。外部喂狗关闭时仍可上报。
应用在 status_init 中绑定唯一回调；status 只记录状态、停止业务、提交日志和刷新指示，不选择动作。

最终 action 为 HOLD 时，由 watchdog 执行 stop(MONITOR)，停止检查并允许继续喂狗，但不清除诊断；
RESET 由私有 request_reset 使用本次 reset_delay_ms 安排复位，内部监控故障默认 200 ms。
业务上报和内部监控故障统一经过 handle_fault：先通知只读回调，再按快照中的 action 执行动作，回调返回值仅作为上报结果。
内部任务超时、健康过期、运行中的 GPIO 故障统一 RESET/200 ms，不推断应用启动阶段。初始化函数直接返回错误，由应用选择上报 HOLD。不自动登记任何任务。
status 只关闭业务、提交日志并刷新故障指示，不直接调用 stop/reset。
延时请求安排后立即返回；等待期间保留可用硬件喂狗，到期的定时器中断只原子停喂并取消检查，再调用底层冷复位，不获取模块锁、不依赖系统工作队列。
RESET 的 reset_delay_ms 为 0 时同步立即复位；重复非零请求保留更早的期限，只能提前、不能延后，也不取消待执行的复位。
定时器按到该期限的剩余时长启动，不要求 64 位绝对超时；延时不支持超过 60 秒，超出时按 60 秒提前。
延时仅给日志线程和串口留出处理机会，不保证打印完成或参数保存。GPIO 已失败或喂狗此前已停用时不会自动恢复，外部芯片可能先于软件期限复位。
工作队列卡死时，故障通知不能运行；硬件定时器仍会按三倍有效期停喂，由外部芯片兜底复位。

复位入口不对外提供，所有业务故障统一通过四参数 watchdog_report_fault 上报；普通调用对 CONTINUE/HOLD 填 0，非零值也不会触发复位。

## 简化后的控制路径

| 原子模式 | 检查任务 | 喂狗 |
| --- | --- | --- |
| UNINITIALIZED | 不检查 | 不喂 |
| MONITORING | 检查 | 要求有效健康期限 |
| FAULTED | 不检查 | 不喂，等待故障通知处理 |
| HOLDING | 不检查 | GPIO 可用时持续喂 |
| RESET_PENDING | 不检查 | GPIO 可用时喂，等待一次性复位定时器 |
| STOPPED | 不检查 | 不喂 |

线程和 ISR 使用同一份模式，不存在 checking/stopped/reset_started 的第二套状态。
初始化是否已尝试由唯一回调是否已经绑定判断，不另外保存 initialized；初始化期间发生停止或复位请求时，不再启动检查/喂狗。
GPIO 失败单独锁存，因为它与 HOLD/RESET 的软件模式独立，不能靠切换模式恢复。
HOLD 不取消已安排的复位；STOPPED 不因后来的 HOLD 重新开始喂狗。
显式 HOLD 或复位请求之后，尚未投递的旧任务/CHECK 故障只保留诊断，不再驱动新的动作；新的 GPIO 故障仍可通知并请求复位。
最终复位回调不获取模块锁；延时请求只在更新 64 位复位期限时短暂持锁，不区分线程/ISR 两套停用实现。

调试不再通过配置关闭软件监控。需要暂停时，可显式调用 watchdog_stop(WATCHDOG_STOP_MONITOR)，本次启动不能重新启用，复位后恢复。该调用不取消已安排的复位。
